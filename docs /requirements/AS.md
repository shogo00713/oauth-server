# 認可サーバーの仕様

RFC 準拠の一般論として要求されている仕様を書いていく

## クライアント登録

- OAuth を使用する前に、個別にクライアントを登録しておく必要がある

- 登録フォーマットは自由だが、次のような情報を集める
    - どこで使われるのか（ブラウザ、ネイティブアプリ など）
    - callback してほしい リダイレクトURL
    - その他アイコン、利用規約など

- 登録の際には、AS が次の2つの情報を返す (confidential)
    - client_id : AS がクライアントを個別に識別する ID
    - client_secret : クライアントであることを当人認証するためのパスワード
- 形式は決まっていないが、認証情報としての機能を持つエントロピーを持たせる

## 認可エンドポイント

- ユーザーから認可を取るために、このエンドポイントが叩かれる
    - GET メソッドのサポートをする、POST メソッドは任意

- クライアントからのリクエストでは、次のパラメータが添えられる
    1. response_type : 必須、ないなら即却下
    1. client_id : 必須
    1. redirect_uri : 任意 (事前登録されているので、複数登録しているなら必須)
    1. scope : 任意
    1.  state : 推奨
    - パラメータのバリューが空なら、それは無視する
    - 知らないパラメータも無視する

- 叩かれた際、AS は次のような処理を行う
    1. 添えられたパラメータが正しく登録されているものなのかなどを確認する
    2. AS 側のユーザーの認証を行う
    3. ユーザーから、クライアントの認可を取る
    4. OK ならば、認可コードの発行を行う
    - 認可が取れなかったなら、そのことを正しく伝える

- 上記の処理が行えたら、認可コードを持ってクライアントに帰る
- 帰り先は、リクエストで添えられていた（=登録された）URL で、それはいじってはいけない
    - クエリが元から含まれていることもあるが、そのまま
    - 同じパラメータを2度入れない
- 次のようなパラメータが添えられる
    1. code : 必須
    1. state : リクエストに含まれていたなら必須

- エラー時は次のようなレスポンスを行う
    1. `error=` : 必須 
        - `invalid_request` : 必須パラメータがない・間違っている
        - `unauthrized_client` : クライアントに、その認可グラントタイプは許可していない
        - `access_denied` : ユーザーが拒否した
        - `unsuported_response_type` : 対応していない認可グラントタイプ
        - `invalid_scope` : スコープがおかしいか、求めすぎ
        - `server_error` : 認可サーバーがぶっ壊れた (リダイレクトで500を伝えれないからこの形を取る)
        - `temporarily_unavilable` : サーバーがメンテ中なので対応できなかった
    2. `error_description` : 任意、人間が読む用に設定しても良い
    3. state : リクエストについていたなら返す


### リダイレクトURL

- 絶対 URL で指定する（登録の際も）
- クエリパラメータを含んで登録してもいいが、フラグメントは NG
- 不正な形式のとき（登録と違うとき）には、その リダイレクトURLに自動的に飛んではいけない
    - 認可サーバー側から、不正な URL であることを伝える

- 攻撃者が、自分の攻撃サイトのURLを指したもので、それを踏ませようとするかもしれない
- 攻撃者の URL に、自動的に認可コードが届くこととなる
    - state ではこれを防げない
    -　これ対策で、リダイレクトURLを発行した先を保存して、アクセストークン発行時とバインドするという対策がある



## トークンエンドポイント

- 認可コードをもらったクライアントが、アクセストークンに引き換えるためにここを叩く
    - POST で来るはず

- クライアントからのリクエストでは、次のパラメータが添えられる
    1. grant_type : 必須
    2. code : 認可コードグラントなら必須
    3. redirect_uri : 認可リクエスト時に提示していたなら必須、public では全必須
    4. client_id : public でクライアント認証ない場合

- トークンエンドポイントを叩かれた上で、認可サーバーは次の対応をする
    1. （できる場合は）クライアント認証を行う
    2. そのクライアントの実体に、認可コードを発行したかどうかを確認する
    3. 認可コードを検証する
    4. （必要な時は）リダイレクトURL を検証する
    5. 以上が全て OK のときに限り、アクセストークンを発行する

- アクセストークンとしてレスポンスする内容は、次を含む JSON として表される（順序は持たない）
    1. access_token : 必須
    2. token_type : 必須
    3. expires_in : 推奨
    4. reflesh_token : 任意
    5. scope : 任意、要求と違うスコープを返すなら必須
    - AS は、レスポンスに no-cache をつけて、キャッシュされないように気をつけなければならない
        - プラグマの対策もするべき？


### クライアント認証
- クライアントのクレデンシャルは機密に扱う
- public とかなら、逆にクライアント認証を信じてはいけない
- クライアント認証ができない場合でも、URL や リソースオーナーへの確認などを求めたりして、対応するべき
    - リダイレクトURLの事前登録を求める
    - どんなクライアントなのかをユーザーに明示する
    - 2回目以降も簡略化しない

### エラー時
- リダイレクトは含まないので、基本的に 400 でレスポンスする
- 次のような内容を含む JSON で通知する
    1.  error : 必須
        - `invalid_request` : トークンエンドポイントへのリクエストに、必須のパラメータが含まれていない、サポートしていないパラメータなど
        - `invalid_clinet` : クライアント認証に失敗した、401 で返してもいい、Basic で言おうとしたなら、401 で、 `WWW-Authenticate` もいる
        - `invalid_grant` : 認可コードとか、リフレッシュトークンが無効
        - `unauthorized_clinet` : クライアントに、その認可グラントタイプは許可していない
        - `susupported_grant_type` : この認可サーバーでサポートしていないグラントタイプ
        - `invalid_scope` : スコープが無効、範囲外です
    2. error_description : 任意、人間に読みやすいためのやつ
    3. error_uri : 任意、エラーの追加情報を、クライアントアプリの開発者が見るため、利用者が見るようではない！
    

### リフレッシュ

- リフレッシュトークンを使用したアクセストークンの発行で、トークンエンドポイントが叩かれることがある
- その際は次のようなパラメータがある
    1. grant_type : 必須、バリューは `refresh_token`
    2. refresh_token : 必須
    3. scope : 任意

- リフレッシュの要請を受けた上で、認可サーバーは次のことを行う
    1. （できる場合は）クライアント認証を行う
    2. そのクライアントに、リフレッシュトークンを発行したかどうかを確認する
    3. リフレッシュトークンを検証する
    4. 以上が全て OK のときに限り、新しいアクセストークンを発行する
    - エラーが起きた場合は、上記と同様に対応する

- リフレッシュに際して、次のことに気を付ける
    - 同時に新しいリフレッシュトークンを発行しても良い (ローテーション)
    - もしそうするなら、クライアントに古いリフレッシュトークンは破棄させる
    - 認可サーバーでは、広報対応用に、少しの間2つ持ち続けても良い
    - スコープは、新旧のリフレッシュトークンで変えない



## 発行形式について

### 　認可コード
- 認可コードのサイズの要求とかはないけど、文書化するべき
- 有効期限は10分が推奨で、同じものを複数回使い回してはいけない
- 発行した認可コードを、client_id と リダイレクトURL でバインドしておく
- 履歴とかに晒される可能性があることを理解して、TLSとかの対策は取ろう
- 使い捨てする

### アクセストークン
- トークンのサイズの要求とかはないけど、文書化するべき
- 有効期限を設定する、推奨は1時間程度 (現代では10分程度？)
- `aud` パラメータを持たせて、RS が自分宛に発行されたアクセストークンなのか確認できるようにする
- 必要に応じて、トークン自体の暗号化も行う
- アクセストークンの改ざんを防ぐために、次のどちらかの形を取る
    1. トークンの内容を MAC やデジタル署名で保護する
    2. 情報は、サーバーの DB で保存し、トークンは情報の参照をするものとする
