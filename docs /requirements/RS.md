# リソースサーバーの仕様

RFC 準拠の一般論として要求されている仕様を書いていく


## リソースサーバーの役割

- クライアントが、アクセストークンを提示して、リソースをもらいに行く
    - 一般的には Bearer 認証の形で、トークンを提示することになる

- その際、RS は次のことを確認する必要がある
    - アクセストークンの有効期限
    - 主張しているスコープの範囲

## アクセストークンの提示と要求

- 次の3つの方法があるが、実質的には1番目のみが来るものと考えて良い
1. Authorization ヘッダー
    - HTTP リクエストの Authorization ヘッダーに Bearer 形式であることを表明して、そのままアクセストークンを添える
    - RS は必ずこの方法を対応する
2. form ボディパラメータ
    - POST を使用して送信される
    - RS は対応してもよい (MAY) 程度
3. URI クエリ
    - 対応しない方がいいので、考えないでいいわ

- 上記のような認証情報の提示がなかった場合は、RS は `WWW-Authenticate` で要求する、その際、次のことを指定する
    - 認証方式では Bearer を使用する
    - 次のようなパラメータを1つ以上含む
        1. relam : 必要とする保護領域
        2. scope : 要求されたリソースへのアクセスに必要とするスコープのリスト
        3. error, error_description, error_uri : エラー通知用
    - エラーは次のようなバリューを取る
        - invalid_request : リクエストで添えたパラメータの形式がおかしい・重複している、400 を返す
        - invalid_token : トークンが期限切れ・おかしな形式・2つ以上、401 を返す
        - insufficient_scope : そのトークンの範囲では対応できない、403 を返して scope で通達してもよい
    - 認証情報の提示がないのは、知らないだけでエラーとは捉えないので、 `error` はつけない
