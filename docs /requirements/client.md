# クライアントの仕様

RFC 準拠の一般論として要求されている仕様を書いていく

## クライアントの要件

- 安全性を踏まえて、クライアントは次の2種類に分けることができる
    1. confidential : 機密情報を安全に保存できる
    2. public : 機密情報を安全に保存できない

- クライアント登録にあたって、各クライアントは自分がどのようなものなのかを明確にする
    - どこで使われるのか（ブラウザ、ネイティブアプリ など）
    - callback してほしい リダイレクトURL
    - その他アイコン、利用規約など

- クライアント登録により、各クライアントには次の情報が与えられる (confidential)
    - client_id : AS がクライアントを個別に識別する ID
    - client_secret : クライアントであることを当人認証するためのパスワード

## 認可エンドポイントを叩く

- ユーザーから OAuth のフローを要請されたときに、この部分が動き出す

- ユーザーからのリクエストは、特にパラメータを含まない
- リクエストを受けて、クライアントは次のことを行う
    1. state を生成して、セッションに紐づけて保存する
    1. （code_verifier を生成して、保存する）
    2. 知っている AS のエンドポイント情報を元に、認可リクエストの URL を構築する
    3. 3xx リダイレクト経由で、AS に向かわせる
    - 向かってもらったら、あとは認可コードを持って帰ってくるのを待つだけ

- 構築する認可リクエストの URL には、次のパラメータを添える
    1. response_type : 必須
    1. client_id : 必須
    1. redirect_uri : 任意 (事前登録されているので、複数登録しているなら必須)
    1. scope : 任意
    1.  state : 推奨
    1. （code_challenge : 任意）
    - 文字列連結などではなく、URL として組む
    - 元から入っているクエリは消さない


## トークンエンドポイントを叩く

- 正常に処理が進んだら、AS がリダイレクトでクライアントの callback を叩く処理をするはず
    - パラメータは正常なら code, state がついているはず

- 次の順番で処理する
    1. 知らないパラメータは削ぎ落として無視する
    2. state　を検証する（一致しないなら、リクエストを拒否）
    3. error があるなら、そのことをユーザーに伝える
    4. code を取り出す

- callback が叩かれている中で、クライアントはさらに AS のトークンエンドポイントを叩く
    - POST メソッドを使用する
- 次のパラメータを添える
    1. grant_type : 必須
    2. code : 認可コードグラントなら必須
    3. redirect_uri : 認可リクエスト時に提示していたなら必須、public では全必須
    4. client_id : public でクライアント認証ない場合
    5. （code_challenge : 任意）
    - 同じパラメータを2回以上入れない
    - confidential の場合は、さらに Authorization ヘッダーで、 client_id と client_secret を添える

- レスポンスとしては、次のようなものが JSON 形式で返ってくる
    1. access_token : 必須
    2. token_type : 必須
    3. expires_in : 推奨
    4. reflesh_token : 任意
    5. scope : 任意、要求と違うスコープを返すなら必須で来る
- 返ってきたものを、クライアント側の DB に入れたり、Cookie に入れたりして、code / state を含まないパスへ飛ぶ
    - Secure 属性がついていない Cookie には入れないし、Secure があるとしても、CSRF 対策を行う
